---
description: 校订 local/ 中的草稿并发布为一篇 blog 文章
argument-hint: "[草稿文件名]"
---
把 `local/` 目录下的草稿校订后，发布为一篇新的 blog 文章。按下面的步骤逐步执行，每一步都要拿到用户确认后才能继续。发布相关的规则遵循 `AGENTS.md` 的《写作与发布流程（Blog / Essay）》。

本次调用指定的目标文件：`${1:-（未指定）}`

## 1. 确定目标文件

- 如果上面的目标文件不是「（未指定）」：把它当作目标文件（参数若不含 `local/` 前缀则补上，如 `local/blog1.md`），确认文件存在后进入第 2 步。
- 否则执行 `ls -lt local/ | head`，取**最近修改的若干个文件（默认 5 个，排除目录）**，用 `ask_user` 把这些文件连同**修改时间 + 文件名**作为选项列出来，让用户确认哪一个是本次要发布的目标文件。
- 必须用 `ask_user` 确认目标文件，不要自行假定、不要跳过这一步。

## 2. 校订草稿

1. 读取目标文件全文。
2. 向用户列出**明显的错误与优化建议**，按严重程度分类排序，建议分类：
   - 语法错误（句子不成立、缺主干／缺介词等）
   - 用词与搭配（生硬、口语堆叠、用词不当）
   - 逻辑与结构（并列不齐、指代错误、前后矛盾、信息缺口）
   - 事实性检查（文中出现的技术名词、API、命令、数据等如有明显错误，一并指出并给出来源依据）
   - 格式与发布问题（缺 front matter、标题重复、标签格式、代码块未标注语言等）
   每条给出：**原文摘录 → 问题 → 建议改法**，尽量给可直接替换的文本。
3. 用 `ask_user` **逐条**向用户确认是否修复（一条一个问题，选项如「按建议修改 / 保持原文」）。条目较多时可先让用户勾选要修的条目，再逐条给出最终改法。
4. 只应用用户确认的修改。**用户选择保留的原文一律不要改**，也不要顺手做未被确认的润色、扩写或删减。

## 3. 发布为 blog

- 用户确认修改完成后，把**最终内容原样**发布为一篇新的 blog 文章：
  - 标题取草稿的一级标题（`# ...`）；正文中去掉该一级标题，其余文字保持原样，不要二次改写或重排结构。
- 生成发布文件（细则见 `AGENTS.md`）：
  - 目录 `_posts/blog/`，分类 `blog` 由 `_config.yml` 的 defaults 自动注入，**不要**手写 `categories`
  - 根据标题生成简洁的英文 slug（全小写、`-` 连接）
  - 文件名 `_posts/blog/YYYY-MM-DD-{slug}.md`
  - front matter 中 `date` 用 `TZ=Asia/Shanghai date "+%Y-%m-%d %H:%M"` 取当前时间，`tags` 为 3-5 个元素的 YAML 数组（中文标签可用）
  - 如果文档引用了图片，把图片拷贝到 `fs/` 目录下，并在文中用 `/fs/{filename}` 引用（文件名建议带日期前缀，如 `17-08-03-xxx.png`）
  - 提交信息：`feat(blog): Add {slug}`
- 写完文件后，向用户展示：文件完整路径、front matter、正文前 200 字摘要、拟用的 commit message，**经用户确认后**再执行 `git add` / `git commit` / `git push`。
- 用户要求修改 → 改完重新展示确认；用户放弃 → 删除已创建但未提交的文件。
